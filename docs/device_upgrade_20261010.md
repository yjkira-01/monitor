# SR112、双 C60E 与桌面设备升级记录

日期：2026-10-10。应用版本：0.3.0；原生 C# / WPF / ONNX / OpenCV。云端训练保持停止，毫米波数据未加入视频模型训练。

## 设备和采集问题

两台 EMEET SmartCam C60E 4K 的名称相同，分别保存 DirectShow DevicePath。当前索引为 0、2；索引只用于本次枚举，设备身份用于重新连接，找不到原设备时不会静默选另一台。同名列表包含集成摄像头和 OBS，所以不能依赖名称或固定索引。

双摄掉帧的对照记录位于 `artifacts/device_upgrade_20261010`：

| 测试 | 条件 | 左路 / 右路 |
| --- | --- | --- |
| `dual_raw.json` | 不加载模型、双独立线程、640×480 | 1.11 / 29.98 FPS |
| `dual_matrix.json` | 旧设置顺序、实际 YUY2；调换打开顺序仍复现 | 慢摄像头约 1 FPS |
| `dual_mjpeg_last.json` | 分辨率、帧率之后设置 MJPEG；实际 FOURCC=1196444237 | 约 30 / 30 FPS |
| `physical_devices_mjpeg.json` | GPU RTMO + GMD；辅助路共享人员模型、不运行 R3D | 30.28 / 30.27 FPS |

根因是 DirectShow 在设置分辨率和帧率时重新协商了采集格式，先设置的 MJPEG 被改成 YUY2。两路未压缩采集时出现明显吞吐下降。把压缩格式放到最后设置后，正序、倒序打开以及 640×360 对照均恢复双路约 30 FPS。仅调整曝光、取消增益写入、串行打开和改采集线程均不能单独修复这个问题。

当前保存的设备设置为 640×480、30 FPS、手动曝光 -5、手动增益关闭。暗光识别仍使用既有预处理；帧率验收不能证明真实夜间识别准确率。

18.22 秒联合识别观测得到左 167 次、右 164 次分析更新，145 次软件配对，接受的配对时间差不超过 80 ms。30 FPS 是视频采集速度，分析调度约 8 Hz，不能混同。测试没有保存用户摄像头画面。

## SR112 固件和基础连接

实测设备为 IWR68XX AOP ES2、SDK `03.05.00.04`，CLI 支持 `vitalsign` 与 `VSRangeIdxCfg`。CP2105 Enhanced 为 COM7 / 115200 控制口，Standard 为 COM8 / 921600 数据口。应用会识别端口组合，并允许手动选择。

内置配置来自设备配套的 AOP 生命体征与人员跟踪例程。它的 `trackingCfg` 最多配置一个跟踪目标，不能据其他例程或合成包宣称当前固件支持多人生命体征。安装高度、水平角和俯仰角由界面填写；现场位置须据实际安装测量。

初始化逐条等待 CLI 确认。用户重新通电后的 `physical_devices_ready.json` 记录 37 条命令全部确认。此前重复初始化曾在 sensorStart 挂起；已增加发送间隔、停止等待、启动超时及先开启数据接收，并在同一运行会话的相同配置仍有效时避免重配。反复重配的可靠性尚未完整验收。设备已在匹配配置下运行时，使用“雷达监测 → 连接数据口”，无需再次初始化；未刷写固件。

后续联合验证 `physical_devices_mjpeg.json` 沿用正在运行的配置，收到 320 帧，约 11.17 Hz，帧号间隙 0，最高 73 点、1 条轨迹，实收 12 次体征输出。接收总帧数包含模型预热时间，18.22 秒只指双摄开始后的观察窗口。

雷达页包含真实三维点云、平面轨迹、Doppler/SNR 明细、目标详情、存在状态、接收字节/帧率/帧号间隙和 TLV 诊断。目标详情复用控件，不因更新收起。配置空间区域后记录连续跟踪下的进入、离开、静息和运动片段；丢失跟踪不算离床。三秒过期清空当前显示；未收到高度包时不启用高度异常规则。观测与诊断可导出 JSON，报告摘要也使用真实雷达数据。

设备体征尚未与医学参考仪器对照。静息不是睡眠分期，存在标志不是人数，点云不是完整人体表面。区域使用雷达跟踪坐标，尚未与视频做空间配准。

## 双目定位

双目页支持两路预览、软件配对、棋盘角点采样、标定、跨视角多人匹配和 17 关节三角化。主监测使用左相机，右相机辅助定位；两个采集源独立工作，人员检测共享 RTMO session 并互斥调用。任一路断开会停止双目、清空场景并恢复连接控件。

没有真实标定时，两路正常预览和识别，但不生成米制坐标。已有标定须与左右设备身份、顺序及实际画面分辨率一致；驱动协商了其他尺寸时也拒绝使用。时间差超过 80 ms、对应有歧义、重投影误差或深度/骨长异常时拒绝测量；缺失关节不冒充实测。三维图形按人员 ID 复用，仅绘制可信测量。

标定方法：将 `Assets/Radar/stereo-chessboard-25mm.svg` 以 A4 横向、100% 比例打印，检查每格确实为 25 mm。默认 10×7 格棋盘对应 9×6 内角点；采集至少 12 组、建议 20 组，覆盖不同位置、距离和倾斜。采样要求两路相差不超过 50 ms，只保留角点，不保存照片。单目及双目重投影 RMS 都须不超过 1.5 px，基线须合理。标定参数保存在原档案目录 `stereo-calibration.json`。

本轮只有软件同步与几何回归，尚未对实际相机完成棋盘标定。合成棋盘完整流程获得 12 组、基线 0.19659 m（真值 0.2 m）、RMS 0.5866 px，这是求解器回归结果，不能当作现场定位精度。普通 USB 摄像头并非硬件同步，运动较快时的深度还需验证。

## 跌倒和稳定性

默认早期 GMD R3D 二分类 + RTMO。Stage C 仍可在设置中选择；模型无新训练。几何异常单独显示为“动作异常 · 请核查”，不再包装成二分类跌倒分数。早期 GMD 的开发滑窗结果存在漏检，不能承诺换回权重就能解决现场问题，完整选模证据保留在 `binary_fall_selection_20261009.md`。

视频开始/停止与切源串行执行；首帧确认后才返回连接成功；采集、姿态和分类分开运行。网络断线清除过期结果，停止或切源不沿用旧分数。坏主档案和坏备份不会导致再次启动崩溃。异常日志仅记录操作、异常类型和堆栈，不记录地址、密钥或私有观测。

可复跑 `desktop/validate-devices.ps1`：CPU/GPU 自检、网络断线/并发切源、四段已知公开视频、八页 UI 和可选实机设备验收；证据保存在独立目录。公开回放是开发回归，不代表外部准确率。

本轮四段实际 GMD 回放中，Subject 1/Fall/01 产生疑似跌倒事件，两段 ADL 未产生跌倒事件；Subject 4/Fall/01 的场景最高分为 0.4902，未触发事件，属于真实漏检。每段分数持续更新，不能把链路运行检查通过转述为四段识别全部正确，也不据这四段调整阈值。证据 `validation/public-replay.json`。

开发验收的 CPU/GPU、三次并发切源和模拟网络视频断开检查通过，断开后旧分析与双目观测清空。八页 UI 公开回放获得 347 次视频更新、114 次姿态更新，422 次单人/整体分数一致性检查，人员详情、七次导航切换、播放操作、1024 px 布局与图标通过。p95 界面更新间隔 61.33 ms，不是分析帧率；长期运行、所有驱动拔插及所有操作组合尚未完整穷尽。
